# 2026-11-09: bug 9, second review of PR #67 after the owner's tests

Follow-up to `2026-11-08-bug-9-review.md`, covering PR #67 commits `ed1ce99` to `b90c8a8` and the owner's two runs of the PR build. Docs only; the full table is in the project's Claude Doc "Review of the Bug 9 analysis and fix (PR #67)".

- **Confirmed on hardware:** screen and area capture, an Explorer window (desktop / window 2.4994) and Chrome in its HDR state (ratio 1.0) all come out at the right brightness. Of the first review's suggestions, the static-desktop stall, the calibration tests, the QA step for Chrome's HDR state, the borderless retry and the "2.0 is measured, not explained" note are done; the owner decided to re-tag 3.0.1.
- **Border:** `GraphicsCaptureAccess` is not registered on the owner's Windows build (`0x80040154`), so `IsBorderRequired(false)` can never take effect there. The fix thread now cuts an uncovered window straight out of the desktop duplication frame (`cropDesktop`, z-order walk over visible, uncloaked windows). Right design, exact pixels, no border. The z-order test is conservative: any transparent overlay window counts as covering and sends the capture down the WGC path, border included.
- **Before release:** `cropDesktop` reads the composed desktop right after the window picker calls `close()` (`tools/windowpicker.cpp:312`), so DWM may not have composed the overlay away yet; that is bug 35's timing on the new path. A `DwmFlush()` (or waiting for one frame with a present) before the duplication closes it.
- **Intermittent 5x capture:** Chrome 5x too bright with Explorer right is Qt's GDI grab, so `grabScreen` returned null once. The new per-capture log (`lightscreen-hdr-last-capture.txt`, appended to `--hdr-report`) will say why. Likely in order: all acquires timing out (no first frame on some drivers until the desktop changes); `DXGI_ERROR_ACCESS_LOST` when the output's colour space changes, which Chrome's swap-chain switch is; `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` while another program duplicates the output. Suggested: recreate the duplication once on `ACCESS_LOST` or on all-timeouts.
- **Speed (224 ms measured vs 52 ms old grab):** use the first acquired frame with or without a present (today up to three 66 MB copies on a static desktop); keep one D3D11 device per adapter for the process; copy only the window or area rectangle off the GPU with `CopySubresourceRegion`.
- **Also:** a Windows-only test for `uncovered`; a QA note that a border flash on an uncovered window means an overlay counted as covering; record `winver` in the bug entry; the QA gate before tagging and the scRGB colour space remain open from the first review.
