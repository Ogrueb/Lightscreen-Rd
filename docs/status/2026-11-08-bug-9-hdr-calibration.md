# 2026-11-08: bug 9 follow-up, the 3.0.1 HDR capture corrected

The owner tested the 3.0.1 draft on the HDR monitor (Windows 11, SDR content brightness 400 nits, i.e. SDR white level 5.0). Area capture was still too bright, window capture was 2.5 times too dark (white 170), and a yellow border flashed on window capture. The draft release is held.

- **Diagnostics:** `HdrCapture::report()`, run with `lightscreen --hdr-report` (writes `lightscreen-hdr-report.txt` to the desktop) or `tst_hdrcapture report`, lists per screen and per Chromium, Explorer or Notepad window: the DXGI output, the SDR white level, failed calls, the most common raw scRGB colours, and Qt's grab for comparison. The project's reachable PC has no HDR monitor, so the owner ran it from the CI zip.
- **Report 1: the desktop path never ran.** In Qt 6, `QScreen::name()` is the monitor's model name ("VP2786-4K"), not the GDI device name, so no DXGI output matched and Qt's grab ran. `HdrCapture::deviceName()` now asks Windows for the monitor at the screen's top left corner.
- **Report 2 (two runs):**
  - The composed desktop (desktop duplication) has SDR white at exactly the SDR white level (5.0), for Explorer and Chrome alike. Dividing by it is right in both of Chrome's states.
  - Qt's GDI grab is right in Chrome's normal state but too bright in the other (GitHub's dark text `0.12` scRGB came out 97 to 131 instead of about 40). That is bug 9 as reported.
  - Windows.Graphics.Capture gives each window at its own scale: Explorer white 2.0, Chrome white 2.0 in its normal state and 5.0 in the other. 3.0.1 divided every window by 5.0, hence 2.5 times too dark. The 2.0 for SDR windows is measured, not explained (no Windows documentation found); the calibration does not depend on it.
- **Window capture fix:** `captureWindow` now takes the window frame and a desktop duplication frame. `HdrCapture::matchScale` compares the two over the window's visible part (per pixel, binned on a log scale; at least half the compared pixels must agree) and the frame is divided by SDR white / that ratio. When it cannot be compared (mostly covered, off screen, rotated panel), PrintWindow runs as before. Nothing about the display is hard-coded (owner's rule).
- **Yellow border:** on Windows 11, `IsBorderRequired(false)` is ignored until the app has asked `GraphicsCaptureAccess::RequestAccessAsync(Borderless)`; that is now asked once per run.
- **Tests:** `tst_hdrcapture` gains `matchScale` (a window 2.5 times dimmer than the desktop, a third covered, plus no match over other content and off the desktop) and `describeScRgb`. A window wholly covered by a single flat colour would match a wrong factor; noted, not handled.
- **Review follow-ups (same PR):**
  - Desktop duplication waited up to a second on a static desktop. It now tries `AcquireNextFrame` 3 times at 100 ms, uses the first frame with a present, and otherwise the last frame acquired.
  - The borderless request is retried on a later capture while Windows has not answered, instead of once per run.
  - New tests `matchScale_sameScale` (ratio 1) and `matchScale_darkWindow` (sparse light text on a dark window, and too few pixels to compare).
  - The QA check says how to force Chrome's HDR state.
  - Deferred: cropping the desktop frame instead of WGC when the window is uncovered; a shared D3D device and copying only the window's region; a QA gate in the release workflow; handling a desktop in the scRGB colour space (only G2084 is treated as HDR).
- **Owner's check of the PR build (2026-11-09):** desktop white 5.0 divided by 5; Explorer window calibrated (desktop / window 2.4994, divided by 2.0005); Chrome in its HDR state calibrated (ratio 1, divided by 5). Brightness right in all three. The yellow border still flashed: `RoGetActivationFactory(GraphicsCaptureAccess)` returns `0x80040154` (class not registered) on the owner's Windows build, so `IsBorderRequired(false)` is accepted but ignored.
- **Border fix:** a window wholly on its output with no visible, uncloaked window above it overlapping (`GW_HWNDPREV` walk, DWM frame bounds) is now cut from the desktop duplication frame, at the SDR white level, without Windows.Graphics.Capture, so no border. Covered windows keep the calibrated WGC path (border possible on such builds). `--hdr-report` shows which path ran and still runs the WGC path for comparison. Cannot be built or tested off Windows; CI builds it.
- **Intermittent too-bright capture (2026-11-09):** with the PR build, one capture over Explorer and Chrome came out with Chrome exactly 5 times too bright (GitHub's folder icon #54aeff as 176,255,255; text #1f2328 as 75,82,93). That matches Qt's GDI grab in Chrome's HDR state, so the desktop duplication path most likely failed for that capture and the fallback ran; the owner could not repeat it. Each real HDR capture now writes its trace to `lightscreen-hdr-last-capture.txt` in the temp folder, and `--hdr-report` (run right after a bad capture) prints it at the end.
- **Second review (2026-11-09):** the first frame acquired is used, with or without a present (was: up to three frames copied waiting for one); on `DXGI_ERROR_ACCESS_LOST` or no frame at all, a new duplication is tried once (a browser switching its swap chain is a likely cause of the one GDI fallback); `DwmFlush()` before cropping an uncovered window, so the closing window picker is not in the desktop frame (bug 35 timing). Deferred: one D3D11 device per process and copying only the needed rectangle (speed only).
- **Release:** the 3.0.1 draft and its tag were made from `4986f90`, before these fixes. See the owner's decision in the thread for whether 3.0.1 is re-tagged or this becomes 3.0.2.
